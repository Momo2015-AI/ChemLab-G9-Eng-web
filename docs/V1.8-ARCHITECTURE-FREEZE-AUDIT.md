## 4. Content/data-source audit

Canonical content enters through `ContentService`.

Canonical knowledge graph:

```text
/content/knowledge/knowledge-graph.json
```

Legacy graph:

```text
/modules/questions/taxonomy/knowledge-graph.json
```

The legacy graph is migration fallback only. Canonical content is attempted first. Graph relations are normalized at the content boundary from legacy `from/to` to canonical `source/target` before reaching the engine.

Questions are registered into the diagnosis question-to-knowledge map at the content boundary. Experiments and knowledge content are likewise loaded through the canonical content service.

**Result: PASS WITH CONTROLLED FALLBACK**

## 9. Freeze rules

From this point forward:

1. Do not create a second application state store.
2. Do not create a second mastery calculation path.
3. Do not create a second knowledge graph engine.
4. Do not create a second diagnosis/recommendation engine.
5. Do not bypass `ContentService` for canonical production content.
6. Do not add new production dependencies on legacy adapters.
7. Keep learning evidence traceable to knowledge targets.
8. Assessment and experiment evidence must share canonical contracts.
9. New features require tests before release.
10. `main` remains the single development and release branch.
11. Directory cleanup must be preserved by automated tests.
