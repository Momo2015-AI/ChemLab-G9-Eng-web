# V1.7 Content Pipeline

## Purpose

V1.7 uses `app/content-service.js` as the application-facing content boundary. The application must not read lesson, question, or knowledge JSON directly from views or controllers.

## Runtime flow

```text
index.html
   ↓
app/bootstrap.js
   ↓
app/application.js
   ↓
app/content-service.js
   ↓
engine/content-loader.js (compatibility adapter)
   ↓
modules/lessons + modules/questions + optional content/
   ↓
ContentService
   ├─ lesson lookup
   ├─ question lookup
   ├─ knowledge graph
   └─ canonical KnowledgeEngine
```

## Current responsibilities

### `app/content-service.js`

The stable application-facing boundary. It owns the loaded content snapshot and constructs the canonical `KnowledgeEngine` from the loaded knowledge graph.

### `engine/content-loader.js`

Compatibility adapter retained during V1.7 migration. It owns URL/path resolution and JSON loading, but it must not become a second application-facing content API.

### Lesson manifest

The loader reads `modules/lessons/manifest.json` and derives lesson file paths from the manifest's `days` entries. Lesson loading must remain manifest-driven; do not hard-code a fixed number of days.

### Question bank

The loader exposes a canonical question array plus a `questionById` index. Knowledge filtering uses each question's `knowledge` identifiers.

### Knowledge graph

The loaded graph is passed once into `canonical-knowledge-engine.js`. Graph traversal and prerequisite logic belong to the canonical engine, not to the content loader.

### Optional content

Topic-bank and experiment/knowledge content are optional compatibility paths. Optional files may return empty/null data where the product contract explicitly permits it; required lesson/question/graph data must fail loudly when unavailable.

## Validation rules

1. JSON files must parse successfully.
2. Lesson files must be discoverable from the manifest.
3. Application code consumes content through `ContentService`.
4. Knowledge traversal is delegated to the canonical KnowledgeEngine.
5. Legacy loader compatibility must remain environment-safe under Node tests.
6. Any content contract change requires corresponding tests before merging.

## Migration rule

Do not delete `engine/content-loader.js` merely because it is named `engine/`. First migrate any direct consumers to `ContentService`, update tests, run the complete baseline, and only then remove the adapter in a dedicated cleanup commit.
