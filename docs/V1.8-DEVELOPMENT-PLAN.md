# ChemLab-G9 V1.8 Development Plan

## 1. Version positioning

V1.7 establishes the stable application architecture and a verified learning-loop baseline. V1.8 is the productization phase: turn the existing learning loop into an actionable, adaptive learning system for Chinese junior-high Grade 9 chemistry.

V1.8 is not a second architecture rewrite. Existing V1.7 boundaries are preserved unless a concrete production requirement proves a boundary insufficient.

## 2. Product goal

The system should answer two questions continuously:

1. What should the learner learn next?
2. Why did the system recommend that task?

The target loop is:

```text
Lesson
  ↓
Knowledge understanding
  ↓
Practice / Experiment
  ↓
Evidence
  ↓
Mastery update
  ↓
Diagnosis
  ↓
Remediation
  ↓
Targeted recheck
  ↓
New evidence
  ↓
Mastery
  ↓
Next-task recommendation
```

## 3. Scope

### P1 — Learning Center 2.0

Create a learner-facing home/dashboard experience that exposes:

- current lesson;
- today's tasks;
- completion progress;
- mastery summary;
- weak knowledge points;
- pending remediation;
- next recommended task.

### P2 — Knowledge/content mapping

Establish explicit mappings among:

```text
Knowledge ↔ Lesson
Knowledge ↔ Question
Knowledge ↔ Experiment
```

The mapping layer becomes the shared semantic contract for assessment, experiment evidence, diagnosis and recommendation.

### P3 — Assessment 2.0

Add diagnostic metadata and adaptive selection while preserving the existing AssessmentController → Evidence → Mastery contract.

Question metadata should support:

- knowledge IDs;
- difficulty;
- question type;
- diagnostic tags;
- answer contract.

### P4 — Diagnosis 2.0

Strengthen the canonical diagnosis engine so that assessment and experiment evidence can produce:

- knowledge target;
- confidence;
- error type;
- supporting evidence IDs;
- recommended action.

Diagnosis must remain separate from remediation policy.

### P5 — Remediation 2.0

Generate actionable personalized paths such as:

```text
review → example → practice → experiment → recheck
```

The path should adapt to learner performance instead of always using a fixed sequence.

### P6 — Experiment Lab 2.0

Integrate experiments into the learning loop:

```text
prediction → operation → observation → explanation → conclusion → evidence
```

Experiment evidence must feed the same mastery/diagnosis contract as assessment evidence.

### P7 — Dashboard 2.0

Turn the dashboard from a passive statistics page into a learning cockpit showing:

- mastery;
- completion;
- experiment ability;
- weak points;
- pending tasks;
- recommendation rationale.

### P8 — End-to-end integration

Add a true full-loop integration test:

```text
enter lesson
→ learn
→ answer incorrectly
→ evidence
→ diagnosis
→ remediation
→ targeted recheck
→ answer correctly
→ mastery improves
→ next task recommended
```

### P9 — Final baseline

Expand the V1.7 baseline from 55 tests toward an 80–100 test range, prioritizing integration coverage rather than artificial unit-test count.

Required CI gates:

- JavaScript syntax;
- Node test suite;
- content/schema validation;
- production entrypoint validation;
- full end-to-end learning-loop coverage.

## 4. Architecture rules

### Keep V1.7 boundaries

```text
app/          application orchestration and services
controllers/  workflow coordination
views/        presentation
engine/       domain engines
core/         canonical domain modules and migration adapters
modules/      primary course/question content
content/      supporting knowledge/experiment content
schemas/      data contracts
docs/         engineering/product documentation
```

### Single source of truth

- ContentService owns application-facing content access.
- Canonical Knowledge Engine owns graph traversal.
- MasteryEngine owns mastery calculations.
- DiagnosisEngine owns diagnosis decisions.
- RemediationEngine owns remediation planning.
- Controllers coordinate; they do not duplicate domain algorithms.

### Compatibility policy

Legacy adapters may remain temporarily when they prevent unnecessary breakage. No new production code may depend on a deprecated adapter. Removal requires a repository-wide import audit and a GREEN baseline.

## 5. Data contracts

The V1.8 semantic model should converge on:

```js
knowledgeId
lessonId
questionId
experimentId
evidenceId
errorType
difficulty
masteryScore
confidence
recommendedAction
```

Every learning event that can affect mastery should be traceable back to evidence.

## 6. Testing strategy

Testing priority is:

1. end-to-end learning loop;
2. cross-module contracts;
3. data/schema validation;
4. domain engine behavior;
5. presentation behavior.

A feature is not complete merely because its unit tests pass. Its evidence must propagate through the canonical learning loop.

## 7. Release gates

A V1.8 phase is complete only when:

```text
implementation
→ tests
→ npm test GREEN
→ CI GREEN
→ documentation updated
→ commit on main
```

No phase should knowingly leave the main branch red.

## 8. Out of scope

Unless explicitly added later, V1.8 does not require:

- a frontend framework;
- a backend service;
- user accounts/cloud sync;
- a second state-management framework;
- a new build system;
- wholesale V1.7 directory restructuring.

## 9. Definition of Done

V1.8 is ready for release when the learner can complete the full loop from a lesson to evidence, diagnosis, remediation, recheck, mastery update and next-task recommendation, and the complete CI baseline remains GREEN.
