# ChemLab-G9-Eng-web V1.7 Development Plan

**Status:** Active
**Baseline:** V1.6 architecture + V1.7 refactor foundation
**Primary goal:** turn the existing module skeleton into one verifiable learning system with a single runtime authority for mastery, knowledge-graph queries, persistence, and learning evidence.

## 1. Development principle

A feature is not considered complete because a module or document exists. It is complete only when the runtime path is connected and testable:

```text
Data → Service/Engine → Learning State → View
```

For learning functions the stronger acceptance path is:

```text
Student action
  → assessment/experiment evidence
  → canonical engine
  → learning state
  → persistence
  → dashboard/recommendation
```

The migration follows a **zero-breakage / behavior-preserving** strategy: establish boundaries first, wire them into the existing runtime, test, then remove legacy implementations.

## 2. Phase 0 — Runtime Stabilization (P0)

### P0-A Mastery runtime wiring

Current risk: `MasteryEngine` exists but learning evidence must be proven to reach it through the real assessment flow.

Tasks:

1. Locate and document the actual quiz/assessment entry point.
2. Introduce/complete an application-facing assessment service/controller boundary based on the actual code, not assumed class names.
3. Convert assessment results into a canonical `LearningEvidence` shape.
4. Send assessment evidence through `MasteryService` to `MasteryEngine.update()`.
5. Persist the canonical mastery state through `ProgressService`.
6. Make dashboard/reporting consume the canonical mastery state instead of recalculating mastery.
7. Remove the old inline `correct/attempts` mastery calculation only after runtime equivalence is verified.
8. Add an end-to-end test: answer → evaluate → mastery update → persistence → reload.

**Acceptance:** a real student answer changes the same mastery state that the dashboard reads, and the state survives reload.

### P0-B Knowledge runtime wiring

Current risk: multiple KnowledgeEngine generations exist while application/dashboard code can still operate directly on graph `nodes`/`edges`.

Tasks:

1. Identify every import/reference to all KnowledgeEngine implementations.
2. Select `canonical-knowledge-engine.js` as the only production implementation, subject to compatibility tests.
3. Initialize the canonical engine at the application/content boundary.
4. Expose a stable query API: `getNode`, `hasNode`, `getPrerequisites`, `getDependents`, `getRelated`, `getExperiments`, `getQuestions`, `getAncestors`, `getDescendants`, and learning-path queries where supported.
5. Replace direct business-layer traversal of `knowledgeGraph.nodes` / `knowledgeGraph.edges` with engine queries.
6. Add graph traversal and compatibility tests.
7. Mark older engines deprecated, then delete them only after reference and runtime checks pass.

**Acceptance:** controllers and views do not implement their own graph traversal; all production graph queries go through the canonical engine.

### P0-C Application boundary

Tasks:

1. Keep `app/state.js` responsible for in-memory state only.
2. Keep `ProgressService` as the persistence boundary.
3. Keep `MasteryService` as the application mastery boundary.
4. Extract router and content/application responsibilities from the legacy application entry point.
5. Reduce `engine/app.js` to compatibility/bootstrap responsibility and remove legacy business logic progressively.
6. Ensure one authoritative dependency graph: Application → services → engines → state/persistence.

**Acceptance:** application startup and the main learning flows work without direct duplicated persistence, mastery, or graph logic.

### P0-D P0 verification

Run and maintain:

- syntax/import smoke tests
- mastery engine tests
- mastery service tests
- progress service tests
- assessment end-to-end tests
- knowledge graph traversal tests
- application routing tests

P0 is complete only when all critical runtime paths are covered and no production code depends on the superseded mastery/knowledge implementations.

## 3. Phase 1 — Learning Engine Integration (P1)

### 1. Canonical LearningEvidence

Define a stable evidence model for assessment, experiment, explanation, retrieval, and transfer activities.

Minimum conceptual fields:

- evidence id
- activity id/type
- knowledge ids
- score/correctness
- evidence weight
- timestamp
- optional diagnostic metadata

All learning activities should produce evidence rather than writing mastery directly.

### 2. Controller/service coverage

Add tests for:

- assessment lifecycle
- experiment lifecycle
- observation recording
- application route dispatch
- persistence/reload

### 3. Content source policy

Make `content/` the canonical educational source. Treat `modules/` as legacy, migration, or derived data unless a documented exception exists.

Write the rule into `content/README.md` and prevent new ambiguous content placement.

### 4. Schema and reference integrity

Extend validation from syntax-only checks to:

```text
Syntax → Schema → ID uniqueness → Cross-reference integrity → Graph integrity
```

## 4. Phase 2 — Educational Content Architecture (P1/P2)

Align schemas with the instructional model. A lesson should be able to represent, where applicable:

```text
Observe
→ Question
→ Predict
→ Learn
→ Experiment
→ Explain
→ Practice
→ Diagnose
→ Remediate
→ Transfer
→ Retrieval
```

Quality requirements such as misconception targets, retrieval opportunities, and transfer tasks should be machine-checkable where they are mandatory for a content type.

## 5. Phase 3 — CI Quality Gate (P2)

CI should verify:

1. JavaScript syntax/imports
2. JSON validity
3. automated tests
4. schema validation
5. reference integrity
6. knowledge graph integrity
7. content-source policy checks

A content/build change should fail CI before publication when a required structural or reference rule is violated.

## 6. Phase 4 — Dashboard and recommendation (P2)

Dashboard becomes a projection of canonical learning state, not a second learning engine.

Target flow:

```text
Mastery + Diagnosis + Knowledge Graph + History
                    ↓
          Recommendation Engine
                    ↓
          Next Learning Activity
```

Recommendations should initially be deterministic and explainable before any more complex personalization is introduced.

## 7. Phase 5 — Experiment integration (P2)

Experiments should contribute learning evidence through:

```text
Prediction → Observation → Conclusion → Assessment → Evidence → Mastery
```

The experiment layer must not independently calculate mastery.

## 8. Phase 6 — Content production (P3)

Only after runtime and schema foundations are stable, scale content production:

- Grade 9 chemistry knowledge graph
- lessons
- experiments
- question bank
- misconception bank
- remediation activities
- transfer tasks
- retrieval activities

Content should be generated and reviewed against the same schema and educational quality gates.

## 9. Phase 7 — Product hardening

After the learning engine is stable:

- responsive/iPad UX verification
- accessibility review
- English educational language review
- performance review
- GitHub Pages production build
- release checklist
- regression suite

## 10. Priority order

| Priority | Work | Exit condition |
|---|---|---|
| P0 | Assessment → Mastery runtime wiring | real answer updates canonical mastery and persists |
| P0 | Canonical KnowledgeEngine runtime wiring | all production graph queries use one engine |
| P0 | Legacy implementation convergence | superseded engines have no production references |
| P0 | Application boundary cleanup | app entry no longer owns duplicated business logic |
| P0 | Runtime regression tests | critical flows are automatically verified |
| P1 | LearningEvidence | all learning activities can emit canonical evidence |
| P1 | Content source policy | canonical content location is explicit and enforced |
| P1 | Controller/service tests | assessment, experiment, application flows covered |
| P2 | Schema + CI quality gates | malformed/invalid content blocks CI |
| P2 | Dashboard/recommendation | dashboard consumes learning state only |
| P2 | Experiment → evidence | experiment outcomes feed learning state |
| P3 | Large-scale content production | content follows runtime/schema contracts |

## 11. Definition of Done for V1.7

V1.7 is not complete when the folder structure looks clean. It is complete when:

- there is one mastery authority;
- there is one production knowledge-graph authority;
- assessment and experiment evidence reach the learning engine;
- learning state is persisted through one boundary;
- dashboard/reporting does not recalculate core learning metrics;
- content has one canonical source policy;
- schemas and reference checks run in CI;
- critical application flows have automated regression tests;
- legacy implementations are removed only after reference/runtime verification;
- the complete student loop can be demonstrated from activity to updated learning state.
