# ChemLab-G9-Eng-web V1.7 Phase 1 Refactor Audit

## Status

Phase 1 has started as a **zero-breakage migration**. Existing V1.6 runtime behaviour is intentionally preserved while new application boundaries are introduced.

## 1. Current runtime boundary

The current `engine/app.js` is the effective application composition root, but it also contains UI rendering, navigation, quiz state, persistence, mastery calculations, experiment orchestration, dark-mode setup and event binding.

Observed responsibilities include:

- application construction and startup
- content loading orchestration
- localStorage persistence
- mastery state mutation
- quiz lifecycle
- answer evaluation
- experiment lifecycle
- route/page switching
- HTML rendering
- DOM event binding
- dark-mode handling

This is the main V1.7 refactor target.

## 2. Current data boundary

`engine/content-loader.js` is already a useful data-access boundary. It loads:

- question bank
- knowledge graph
- lesson manifest
- topic bank
- 36 lesson records
- experiment records
- knowledge content

It should remain the canonical loader during the first migration phase.

## 3. Current navigation boundary

`engine/router.js` exists, but the application still controls navigation through `currentPage` and direct rendering inside `ChemLabApp`. This creates two competing navigation models.

V1.7 target:

```text
URL / Router
      ↓
Application State
      ↓
Feature Controller
      ↓
View
```

No feature should directly invent its own routing mechanism.

## 4. V1.7 migration boundaries introduced

### `app/state.js`

Provides a stable state boundary and keeps the existing `chemlab_v16` persistence key for backwards compatibility.

New code should use this boundary instead of directly reading/writing `localStorage`.

### `app/bootstrap.js`

Provides the new application composition root. During the migration it deliberately imports the V1.6 runtime so that existing behaviour remains unchanged.

The next phase will move dependency wiring from `engine/app.js` into this module.

## 5. Required next extraction order

Do **not** rewrite the whole application at once.

Extract in this order:

1. `AppState` / persistence adapter
2. router adapter
3. content service
4. learning-flow controller
5. assessment controller
6. experiment controller
7. dashboard/diagnosis service
8. view/rendering layer
9. legacy `ChemLabApp` removal

Each extraction must preserve the existing public behaviour before the next extraction starts.

## 6. Content architecture principle

The educational model should become independent of UI:

```text
Curriculum
   ↓
Knowledge Model
   ↓
Lesson Model
   ↓
Experiment Model
   ↓
Assessment Model
   ↓
Mastery / Diagnosis
   ↓
Recommendation
   ↓
UI
```

The UI must never become the source of truth for educational rules.

## 7. Learning-science direction

Future content work must follow a student learning loop rather than a page-count model:

```text
Observe
  ↓
Question
  ↓
Predict
  ↓
Learn / Model
  ↓
Experiment
  ↓
Explain
  ↓
Practice
  ↓
Diagnose
  ↓
Remediate
  ↓
Transfer
```

For chemistry specifically, lessons should repeatedly connect:

- macroscopic phenomena
- particle-level explanation
- chemical symbols / equations
- evidence from experiments
- quantitative reasoning
- real-world application

## 8. Quality gates for every future content module

A lesson is not considered complete merely because it contains text and questions. It should have:

- explicit learning objectives
- prerequisite knowledge
- concept explanation
- misconception targets
- observable evidence or examples
- guided practice
- independent practice
- feedback/explanation
- retrieval opportunity
- transfer/application task
- assessment tags
- knowledge-point mapping

## 9. Known technical risks to resolve

### A. Duplicate responsibility

`engine/app.js` and `engine/router.js` both participate in navigation.

### B. Persistence coupling

`ChemLabApp` directly owns persistence through `localStorage`.

### C. Rendering coupling

Business rules and HTML templates are mixed in the same class.

### D. Content-source ambiguity

The repository contains both `modules/` and `content/`. Their roles must be formally separated before large-scale content expansion.

### E. Validation depth

Current CI validates JavaScript syntax and JSON syntax, but not runtime module resolution, schema correctness or critical learning flows.

## 10. Definition of done for Phase 1

Phase 1 is complete when:

- `bootstrap.js` is the real browser entry point
- application state is no longer owned by `ChemLabApp`
- router is the single navigation authority
- content loading is accessed through a service boundary
- `ChemLabApp` becomes a thin compatibility facade or is removed
- existing courses, quizzes, experiments and dashboard behaviour remain functional
- CI validates module paths and content schemas

Until those conditions are met, the old engine must not be deleted.
