# V1.7 Content Source Policy

## Decision

`content/` is the canonical educational content source for V1.7.

It owns the authoritative learning model and semantic data:

- curriculum and lesson definitions
- knowledge concepts and graph relations
- questions and assessment metadata
- experiments and evidence models
- misconceptions and remediation metadata
- content schemas

Runtime code must consume this source through `app/content-service.js` or an explicit repository/loader adapter. UI files must not become authoritative content stores.

## Runtime boundary

`modules/` is reserved for runtime modules, adapters, indexes, generated artifacts, or compatibility code. It must not contain a second manually maintained copy of canonical lesson/question/knowledge content.

If a build process creates derived files under `modules/`, those files are disposable and must be reproducible from `content/`.

## Naming rule

A concept, lesson, question, experiment, or misconception must have exactly one canonical content record. IDs are stable identifiers and must not be reused for a different concept.

## Migration rule

During V1.7 migration, legacy data may be read through adapters, but new content must be added only to `content/`. Legacy copies should be removed once all consumers are migrated and CI confirms that no runtime import depends on them.

## Validation rule

CI must validate canonical content against its JSON Schemas and reject malformed or incomplete records before deployment.

## Why this boundary exists

The project previously accumulated parallel implementations while moving from the V1.5/V1.6 page-oriented model to the V1.7 learning architecture. A single source of educational truth prevents content drift and lets the learning engine, dashboard, diagnosis system, and future recommendation system operate on the same evidence model.
