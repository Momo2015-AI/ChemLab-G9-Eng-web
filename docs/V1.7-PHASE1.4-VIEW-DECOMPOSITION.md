# V1.7 Phase 1.4 — View Decomposition

## Status

The application now has an explicit composition root and a transitional view registry. The legacy renderer remains the source of truth while views are migrated one at a time.

## New structure

```text
app/
├── application.js      # composition root
├── bootstrap.js
├── router.js
├── state.js
└── content-service.js

controllers/
├── learning-controller.js
├── assessment-controller.js
└── experiment-controller.js

views/
└── view-registry.js    # temporary adapter
```

## Why a registry first?

The current `engine/app.js` owns all rendering methods. Moving those methods blindly would create circular dependencies and duplicate state. The registry gives us a stable view contract first:

```js
view.render() -> HTML string
```

Each view can then be migrated independently to a dedicated module.

## Migration order

1. Home
2. Course / lesson
3. Quiz
4. Result
5. Knowledge graph
6. Dashboard
7. Experiment
8. Experiment result

## View contract

A migrated view should:

- receive data/state through arguments
- return/render UI only
- never call `fetch()` directly
- never write `localStorage` directly
- never calculate mastery or diagnosis
- never contain chemistry-domain rules

## Next step

Migrate `home` and `course` first because they have the lowest state coupling. After those are stable, migrate quiz/result and then experiment/dashboard.
