# ChemLab-G9-Eng-web V2.0 Architecture Audit

Date: 2026-08-12
Scope: production frontend, startup lifecycle, content boundary, routing, deployment workflow, CI gates.

## Executive summary

The repository had accumulated several version layers (V1.7/V1.8/V1.9/V2.0) around one runtime. The most important production defect was a startup lifecycle coupling: the bootstrapper waited for canonical content hydration before starting the router. A second class of risk came from deployment-specific URL assumptions and duplicated CI responsibilities.

## Findings

### P0 — startup blocked by content hydration

`bootstrap.js` mounted the shell and then awaited `contentService.load()` before `application.start()`. Any slow, unavailable, or malformed content request therefore left the initial shell in the startup state.

**Resolution:** bootstrap now starts the application immediately. The application owns background content hydration and re-renders the active route after content becomes ready.

### P0 — content loader had no request deadline

`fetch()` requests could remain pending without a bounded failure path.

**Resolution:** `ContentLoader` now uses an AbortController timeout (12s by default), clears failed cache entries, and surfaces a diagnostic error.

### P1 — deployment-specific `<base>` coupling

The previous architecture depended on a hard-coded GitHub Pages `<base>` path. This is incompatible with root-path local/static previews.

**Resolution:** the `<base>` dependency was removed; content assets are resolved from `import.meta.url`.

### P1 — duplicate CI health workflow

`build-check.yml` and `check.yml` duplicated health validation responsibilities.

**Resolution:** health/runtime validation is consolidated into `build-check.yml`; redundant `check.yml` was removed.

### P1 — CI did not validate the production import graph

Node syntax tests alone did not prove that every relative production import target existed or that deployment-specific assumptions were absent.

**Resolution:** `scripts/runtime-audit.mjs` now checks the canonical entry point, relative JS import targets, deployment base assumptions, common hyphenated identifier mistakes, and the single Pages workflow contract.

### P1 — lesson content was already moved toward lazy loading

The loader now returns lightweight manifest metadata and loads lesson bodies on demand. This remains the correct direction and is retained.

## Target runtime architecture

```text
index.html
  -> app/bootstrap.js
      -> frontend/shell/portal-shell.js
      -> app/application.js
          -> router starts immediately
          -> home shell renders immediately
          -> contentService hydration runs in background
              -> question bank
              -> knowledge graph
              -> lesson manifest
              -> topic bank
          -> active route re-renders when content is ready

course/:day
  -> lesson body loaded on demand
```

## Architectural rules frozen after audit

1. `bootstrap.js` must not directly block on `contentService.load()`.
2. `application.start()` owns startup hydration.
3. Content requests have explicit timeouts.
4. No deployment-specific `<base>` tag is allowed.
5. Relative production imports must resolve to real files.
6. Only `deploy-pages.yml` is the canonical Pages deployment workflow.
7. Lesson bodies remain lazy-loaded.
8. CI must test both the application contract and production import/deployment invariants.

## Remaining cleanup

The repository still contains historical view names such as `v19-*` and compatibility APIs because content and learning-controller contracts depend on them. These should be removed only after a dependency-graph migration, not by blind deletion. The current release therefore prioritizes runtime correctness and explicit boundaries over cosmetic renaming.

## Verification gate

The repository must pass:

- `npm test`
- `node scripts/runtime-audit.mjs`
- `npm run audit:content`
- JS syntax validation
- JSON validation
- GitHub Pages deployment

A green CI result is necessary but not sufficient for browser verification; the deployed page must also render the home surface rather than the startup placeholder.
